### Added

- `Flow.Env` with `args`, `var`, `var_or`, `has_var`, `cwd`, and `home_dir`
  (proposal 0178, item 5), plus a new fine-grained `Env` effect that coarsens
  to `IO` alongside `Console`, `FileSystem`, and `Stdin`.

  Reading the environment is ambient input — it makes a function
  non-deterministic in the way filesystem access does — so it is visible in
  signatures rather than silent. A function that consults `$HOME` says so.

  The return types differ deliberately: `var` and `home_dir` return `Option`,
  because an unset variable is an ordinary condition, while `cwd` returns
  `Result<String, IoError>`, because the working directory can be deleted out
  from under a running process.

- Programs can receive command-line arguments. Everything after a `--`
  separator is passed through to the running program untouched:

  ```text
  flux run build.flx -- --target native -v
  ```

  `Env.args()` reports them with the script path first, matching `argv[0]`
  convention, so a Flux tool can name itself in its usage text. The separator
  is what lets a program accept flags that `flux` itself would otherwise claim
  or reject as unknown.

  Both backends agree: the VM driver synthesizes the argv, and the native
  backend forwards the arguments to the compiled binary and overrides `arg0`
  so the script path leads there too, rather than the internal cache path.

### Changed

- The `IO` effect alias now expands to `<Console | FileSystem | Stdin | Env>`.
  Diagnostics that print an expanded `IO` row therefore include `Env`, and the
  `examples/type_system/failing/` fixtures that assert on that text have been
  updated to match. `Env` is discharged at the root boundary like the other
  built-in I/O effects, so `fn main() with IO` needs no explicit handler.
